33.16 Counting Columns ¶

The column functions convert between a character position (counting characters from the beginning of the buffer) and a column position (counting horizontal screen positions from the beginning of a line).

These functions count each character, image, and stretch of white space according to the number of columns it occupies on the screen. This means characters count according to their display width, control characters count as occupying 2 or 4 columns, depending upon the value of ctl-arrow, tabs count as occupying a number of columns that depends on the value of tab-width and on the column where the tab begins (see Usual Display Conventions), and composed sequences of characters and Emoji sequences count according to the width of the glyphs shown to display them. By default, the display width of character is according to display tables, if any, which affect its display (see Display Tables), images and stretches of whitespace count according to their width on display (see Other Display Specifications), and characters which have the invisible text property, and therefore are not shown on display, are not counted at all, unless buffer-invisibility-spec specifies that invisible text should be displayed as ellipsis (see Invisible Text).

Variable: column-ignore-props ¶

If this variable is non-nil, counting columns ignores display tables, display properties, and invisible properties. Thus, characters of buffer text are counted for their display width regardless of whether they are visible on the screen and whether the display table in effect or the display properties change how they are shown, and images are counted as if the underlying buffer text was shown instead of each image. This variable intended to be bound non-nil when columns are counted for the purposes of indenting text, because text indentation usually disregards whether and how the text is shown.

Column number computations ignore the width of the window and the amount of horizontal scrolling. Consequently, a column value can be arbitrarily high, larger than the window width. The first column is numbered 0; this is usually the leftmost column, but when bidirectional text is reordered for display (see Bidirectional Display), the leftmost column on the screen might not be column 0, because columns are counted in logical order, not in visual order. Also, in right-to-left paragraphs, column 0 is the rightmost one, at the right edge of the window.

Function: current-column ¶

This function returns the horizontal position of point, measured in columns, counting from 0 at the beginning of the current physical line. The column position is the sum of the widths of all the displayed representations of the characters between the start of the current line and point.

Command: move-to-column column &optional force ¶

This function moves point to column in the current line. The calculation of column takes into account the widths of the displayed representations of the characters between the start of the line and point.

When called interactively, column is the value of prefix numeric argument. If column is not an integer, an error is signaled.

If it is impossible to move to column column because that is in the middle of a multicolumn character such as a tab, point moves to the end of that character. However, if force is non-nil, and column is in the middle of a tab, then move-to-column either converts the tab into spaces (when indent-tabs-mode is nil), or inserts enough spaces before it (otherwise), so that point can move precisely to column column. Other multicolumn characters can cause anomalies despite force, since there is no way to split them.

The argument force also has an effect if the line isn’t long enough to reach column column; if it is t, that means to add whitespace at the end of the line to reach that column.

The return value is the column number actually moved to.
